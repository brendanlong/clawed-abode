# Messages & Real-Time Streaming

## Classification

Every SDK message routes through `classifyMessage` ([`src/lib/claude-messages.ts`](../src/lib/claude-messages.ts)) → `stream_event` | `skip` | `persist`. It switches over the SDK's `SDKMessage` union and ends in `assertNeverFallback`: a new top-level message type fails the build until handled, while at runtime an unrecognized type degrades to generic system persistence so an unexpected frame never crashes the query loop.

`system` subtypes fall into three buckets (not compile-time exhaustive; unknown subtypes get a safe default):

1. **Ignored** (never persisted): pure progress ticks (`thinking_tokens`, `task_progress`, `api_retry`, …) — `IGNORED_SYSTEM_SUBTYPES`.
2. **Visible**: `error`, `compact_boundary`, `model_refusal_fallback` — these carry signal. `model_refusal_fallback` marks a silent primary→fallback model downgrade after an API refusal; without a visible banner the downgrade would be invisible. The primary model's retracted attempt (`retracted_message_uuids`, matched against each message's SDK `uuid`) is folded under the banner, collapsed, rather than shown alongside the fallback's redo. Retraction undoes the model's turn, not its tool calls' side effects, so the fold says so, and a retracted subagent spawn stays in the transcript.
3. **Hidden**: everything else is **persisted but not rendered**. Persisting keeps the option of widening the visible set later without a backfill.

Messages the CLI injects itself — another session's `SendMessage`, an MCP channel — only reach us as replays, so the CLI runs with `--replay-user-messages`. That also echoes every prompt we push; the runner drops a replay whose uuid it pushed (the prompt was persisted at send time) before it reaches status or persistence. Every other replay is real content (slash-command output arrives as a replay too). Injected messages carry an `origin` and render as "From _sender_", never as the user's own prompt; a sending session is resolved by its agent name (`sessions.byAgentName`) and shown as its title, linked to it. Background-task reports (`origin.kind: 'task-notification'` — Monitor events, finished background commands and subagents) are mostly noise to the user, so they render as one collapsed line with the `<summary>`.

The composer's slash commands are not messages: [`session-commands.ts`](../src/server/services/session-commands.ts) keeps the SDK's list per session, replaced wholesale by `supportedCommands()` and each `commands_changed`, and hides init's `terminal_slash_commands` (terminal-UI commands like `/doctor` are meaningless on a phone).

Other rendering-relevant classification: `server_tool_use` (e.g. the advisor, which runs inside the API and never passes `canUseTool`) renders as a one-line indicator; a message whose only block is an encrypted `advisor_tool_result` is hidden (nothing human-readable to show). Claude Code requests thinking with `display: "updates"`: reasoning arrives as empty `thinking` blocks (rendered as nothing), and a `thinking` block with text is a [progress update](https://platform.claude.com/docs/en/build-with-claude/thinking#progress-updates) addressed to the user, so it is treated as ordinary assistant text everywhere (rendering, copy, voice, cross-session transcripts) via `assistantBlockText` in [`claude-messages.ts`](../src/lib/claude-messages.ts).

## Storage & Pagination

[`message-store.ts`](../src/server/services/message-store.ts) owns all `Message` row access, reads included; routers never query `prisma.message` or decode `content` themselves. Messages carry a per-session monotone `sequence`. **Every insert goes through `insertMessage`**, which reserves a sequence with a single autocommit `UPDATE "Session" SET "messageSequence" = "messageSequence" + 1 … RETURNING` — one statement, so SQLite serializes it on the write lock and concurrent inserts can't collide.

A duplicate `id` (e.g. an idempotent synthetic `tool_result`) fails the primary key and is treated as a no-op; the reserved sequence is skipped, leaving a gap — pagination orders by `sequence` and never assumes contiguity. All history queries are cursor-based on `sequence` (`claude.getHistory` pages backward from the newest).

A stored message is only ever rewritten by `markLastMessageAsInterrupted`, and only ever deleted for a prompt Stop pulled back before the agent read it (`message_removed` tells clients to drop it — see [`claude-sessions.md`](claude-sessions.md)). Everything else is append-only, which is what lets the client cache dedupe live messages by id instead of reconciling them.

## SSE

All server→client updates flow over SSE via tRPC's `httpSubscriptionLink` (client→server is plain mutations). Because the link opens one `EventSource` per subscription, the app uses exactly **two streams**:

1. **Per-session multiplexed stream** (`sse.onSessionEvents`) — opens on every (re)connect with a `snapshot` of the session row, its latest-value fields, and the transcript ([`session-snapshot.ts`](../src/server/services/session-snapshot.ts)), then streams deltas: a discriminated union of every event kind emitted as-is on one in-process channel per session by [`events.ts`](../src/server/services/events.ts). **The server subscribes to that channel before reading the snapshot**, so snapshot + deltas has no gap; a delta the snapshot already reflects is harmless (messages dedupe by id, latest-value events converge). Client side, [`useSessionStream`](../src/hooks/useSessionStream.ts) is the only writer of the session's caches; nothing on the session page refetches, and mutations rely on the stream to announce their change. Returning to the tab or coming back online starts a fresh connection, so each return gets a snapshot.
2. **Global session-list stream** (`sse.onSessionListEvents`) — opened exactly once, by `SessionListStreamProvider` ([`src/lib/session-list-stream-context.tsx`](../src/lib/session-list-stream-context.tsx)); consumers register handlers via `useSessionListEvent` rather than subscribing themselves (a second `useSubscription` would be a second `EventSource`). Session changes, turn-state flips, and background-set flips all fan here as lightweight signals (a session change carries only `sessionId`/`name`, not the row); any event just triggers a `sessions.list` refetch, which carries the authoritative `turnActive` / `backgroundActive`, so reload/tab-switch/reconnect resync to the server's in-memory truth rather than trusting streamed state. It also carries `attention` for the notifier (see [`claude-sessions.md`](claude-sessions.md#needs-you)). The session-list badge derives running / background / waiting from the two axes (`deriveSessionDisplayStatus`); a dedicated `background` signal covers background-set flips that produce no `running` edge (a task settling with no continuation, or a ✕-stop).

**Backpressure.** tRPC pulls from the subscription generator only when the response stream has room, so each subscriber's in-process buffer (`createEventQueue`) is capped: on overflow it is discarded and a `resync` event is yielded instead. Events that carry their whole state coalesce in the buffer, so the cap is a real memory bound: each latest-value kind keeps only its newest, and partial-message snapshots keep one entry per streaming agent (the main agent and each subagent stream concurrently, so partials are keyed by `parent_tool_use_id`) rather than one per delta ([`sessionEventCoalesceKey`](../src/server/routers/sse.ts)). Only persisted messages and removals count toward the cap. The per-session stream answers an overflow with a resumed-style snapshot from its watermark (below), which also heals a dropped `message_removed`; the session-list stream yields `resync` and the client refetches the list.

**Session list.** `sessions.list` is keyset-paginated on `(lastActivityAt desc, id desc)` via [`src/lib/keyset-page.ts`](../src/lib/keyset-page.ts) with an explicit `select`; the home page runs the active and archived lists as two independent infinite queries. PR status is served from `Session.pullRequest`, never fetched inside the list query: `detectBranchAndPr` links the session to its branch's PR at each turn end and the resulting `session` event reaches both streams, so the list and the session header read it from the row.

**One copy of PR state.** What GitHub last said about each PR — including the CI rollup for its head commit — lives in one `PullRequest` row, shared by badge lookups and [PR watches](claude-sessions.md#pull-request-watches) so the badge always matches what a watching agent is told. `Session.pullRequest` is a copy of the linked row's `info`, made in SQL from the row itself by [`pull-request-store.ts`](../src/server/services/pull-request-store.ts), the only writer of either; the copy (rather than a join) exists because session updates are announced from `updateManyAndReturn` rows, which can't include relations. Every write is guarded by when its lookup started, so overlapping lookups can't put an older answer over a newer one.

**PR freshness.** A turn-end write alone goes stale the moment the agent stops — a PR opened, reviewed or merged afterwards would never appear, and GitHub can't notify us (the server has no public ingress). So `sessions.list` and every session-stream snapshot also hand their rows to `refreshStalePullRequests`, which queues the ones whose `prCheckedAt` has aged out ([`src/lib/pull-request.ts`](../src/lib/pull-request.ts)) without the response waiting on GitHub, and announces any change over SSE. Polling only what's on screen keeps the cost bounded by page size per TTL rather than per request (which is also why the list refetches on mount and tab focus, and the session page reconnects on tab focus, rather than trusting what it has — that is what re-arms the poll); a bounded worker pool keeps one list read from opening a burst GitHub would answer with a secondary rate limit. `prCheckedAt` is stamped even when the lookup fails, so a repo the token can't read — a fine-grained PAT missing **Pull requests: read** 403s on private repos while public ones still work — costs one call per TTL instead of one per view.

The TTL is short (a minute) because unchanged lookups, checks included, are free conditional requests ([`github.ts`](../src/server/services/github.ts)). The agent's own branch/PR changes don't wait for the turn to end: a `PostToolUse` hook schedules a debounced `detectBranchAndPr` after tool calls that may change them (`prToolEffect`) ([`pull-request.ts`](../src/lib/pull-request.ts)).

**Resume.** The subscription input is just `{ sessionId }`. Each event is wrapped in `tracked()` with a `watermark:counter` id ([`src/lib/sse-resume.ts`](../src/lib/sse-resume.ts)):

- `watermark` = highest **persisted** message sequence delivered (snapshot or delta). A snapshot carries the newest history page, widened on a reconnect (`lastEventId`) to everything after the watermark, plus the in-progress partials. It is authoritative for its range: its rows replace cached ones and cached messages the server no longer has are dropped, which heals a `message_removed` missed while disconnected (the row is gone, so it can't be replayed). When the cache reaches into that range, older cached pages (the user's scroll-back) stay; otherwise the snapshot replaces the cache ([`applyHistorySnapshot`](../src/lib/message-cache.ts)).
- `counter` = strictly increasing per connection, seeded from the previous `lastEventId`, so ids never repeat across reconnects (tRPC drops repeated tracked ids).

`EventSource` auto-reconnects with `Last-Event-ID`; a `ConnectionStatusIndicator` banner shows while the stream is down, with a manual Reconnect once it has given up (a non-retryable error, e.g. an HTTP 503 the polyfill won't retry). Only a `NOT_FOUND` reads as "Session not found". Ping/reconnect tuning lives in [`src/server/trpc.ts`](../src/server/trpc.ts).
